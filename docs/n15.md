# Bloco N15 — Governança (Fase 1)

## Visão geral

O N15 é a camada de **aprovação governada** do Cerberus Finds Archive. Ele atua como um **gatekeeper fail-closed** entre a curadoria (N13) + scoring comercial (N14) e qualquer ação executável (Publish, Acquire Affiliate, Distribute, Advertise). O N15 **nunca executa ações**: ele apenas **autoriza ou bloqueia**, registrando cada decisão com rationale completo, requisitos verificados e digest das avaliações de origem para auditoria.

> Regra fundamental: **CANDIDATE != FACT CANÔNICO** e **ASSESSMENT != ACTION**. A decisão de governança é uma autorização auditável, não uma execução.

## Princípios de design

| Princípio | Implementação |
|---|---|
| Fail-closed | Qualquer erro, dado ausente ou ambiguidade resulta em `BLOCKED` (ou `REVIEW` quando a política define status de revisão), nunca em aprovação implícita. |
| Gates obrigatórios | `N13 PASS` (curadoria aprovada) + `N14 score válido` (scoring comercial) são pré-condições absolutas. |
| Determinismo | O `decision_digest` (SHA-256) é derivado de um payload estável: candidato, ação, status, versão de política, digests N13/N14, score, band, authorization scope ordenado e `reference_date` truncada ao dia UTC (hora descartada). |
| Idempotência | `idempotency_key` = digest determinístico do snapshot; colisão de chave única (PostgreSQL 23505) resolve via `resolveReplay`, retornando `identical_duplicate` com a decisão já existente. |
| Isolamento | O engine é **puro**: sem acesso a banco, sem efeitos colaterais, sem execução de Publish/Advertise (`is_actionable = false` sempre). |
| Auditoria | Toda decisão persiste na tabela `candidate_assessment` com `filter_version = 'n15:governance_v1'`, carregando rationale, requisitos, digests de origem e evidências. |

## Arquitetura

```
Telegram/Operator (admin)
        │
        ▼
POST /api/commercial/governance/decide   ← requireAdminAuth
        │
        ▼
  service.ts (orchestration)
  ├─ resolveCandidate(candidateId)        ← fail-closed se infra falhar
  ├─ loadN13Assessment / loadN14Assessment (candidate_assessment)
  ├─ listCandidateEvidence (proveniência real do candidato)
  ├─ buildCandidateSnapshot               ← snapshot determinístico
  ├─ deriveAuthorizationContext (admin)
  ├─ findIdenticalN15Decision             ← replay idempotente
  ├─ engine.ts → evaluateGovernance       ← lógica pura, fail-closed
  └─ persistAssessment                    ← idempotency_key dedup
```

### Persistência

O N15 **reutiliza a tabela `candidate_assessment`** (Bloco N4), evitando uma segunda tabela de assessment e compartilhando o índice composto `(candidate_id, filter_version, created_at)` criado pelo N14. O repositório `candidateAssessmentRepository.ts` exportou `ASSESSMENT_KINDS` com o novo valor `n15:governance_v1`, espelhado no CHECK da migration e no teste A01 do filtro.

Campos da linha N15:
- `filter_version = 'n15:governance_v1'`
- `dimensions.status` = APPROVED | REVIEW | BLOCKED
- `dimensions.action` = PUBLISH | ACQUIRE_AFFILIATE | DISTRIBUTE | ADVERTISE
- `classification` = WINNER (APPROVED) | HIDDEN_GEM (REVIEW) | NOT_RECOMMENDED (BLOCKED)
- `recommendation = NONE` (o N15 não emite recomendações de ação)
- `is_actionable = false` sempre
- `idempotency_key` = digest determinístico do snapshot

## Engine (lógica pura)

O `evaluateGovernance` valida na ordem: candidato válido → N13 existente com verdict PASS → N14 existente com band conhecida e score finito → consistência band/score → score >= min da política → evidência suficiente (evidence_refs ou observações conhecidas do candidato) → proveniência conhecida (prefixo `n10:`) → autorização do operador (action no authorization_scope) → risco aceitável → frescor N13/N14 (TTLs) → requisitos específicos da ação (ex.: `publish_previously_authorized` para ADVERTISE).

Hard gates → `BLOCKED`. Estaleness com `stale_status = REVIEW` → `REVIEW`; com `BLOCKED` → `BLOCKED`. O requisito `publish_previously_authorized` verifica a existência de uma decisão PUBLISH APPROVED vigente para o candidato (via consulta de estado) — por isso é satisfeito apenas no service com persistência, não no engine puro isolado.

### TTLs padrão

| Ação | N13 TTL | N14 TTL | max_risk | stale_status |
|---|---|---|---|---|
| PUBLISH | 168h (7d) | 72h (3d) | 0.5 | REVIEW |
| ADVERTISE | 168h (7d) | 48h (2d) | 0.3 | BLOCKED |

## Determinismo e digest

`decision_digest = SHA-256(stableJson({ candidate_id, action, status, policy_version, n13_digest, n14_digest, score, band, authorization_scope, reference_date }))`, com `reference_date = truncateToDayUtc(nowIso)` (bug corrigido nesta fase: o truncamento anterior preservava a hora). `decision_id = gov-{candidate_suffix}-{action}-{digest}`.

## Segurança

Rotas protegidas por `requireAdminAuth`. Sem credenciais ou senha nos logs (padrão do projeto). Fail-closed em qualquer erro de infraestrutura: erro de leitura do candidato → `internal_error` com decision BLOCKED; ausência do cliente Supabase → `internal_error` com decision BLOCKED.

## Dívidas conhecidas / limitações

- O mock de teste compartilha a última linha inserida (`insertedRow.data`); testes de colisão multi-persistência do mesmo client são limitados ao padrão real (resolvido apenas para os fluxos existentes).
- `requireClient()` foi exportado do `candidatesRepository.ts` apenas para o service N15 (impacto mínimo, sem mudança de comportamento).
- O gate `publish_previously_authorized` depende do estado de decisões PERSISTIDAS; no engine puro ele nunca se satisfaz (documentado nos testes).
- Rota `GET` read-only usa `requireAdminAuth`; a leitura não grava nada.
